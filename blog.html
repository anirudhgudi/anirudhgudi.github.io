Robotics Software · ~9 min read

ROS 2, from a mechanical engineer's seat

The first time I opened a ROS 2 workspace, I'd already wired a Raspberry Pi to a PCA9685 servo driver by hand for Snakebot, so I assumed I understood "software talking to hardware." I didn't — not the way ROS 2 wanted me to. This is the explanation I wish I'd had: nodes and topics explained the way a mechanical engineer already thinks about assemblies and wiring harnesses, then the parts that actually got me stuck later.

Beginner Intermediate Advanced

Beginner Nodes are components, topics are the harness

Before ROS 2, my Snakebot code was one Python script: read a sensor, compute a servo angle, write it out, repeat. It worked, but it didn't scale — every new sensor meant threading it into the same monolithic loop.

ROS 2 splits that loop into nodes — independent programs that each do one job. A camera driver is a node. A footstep planner is a node. A motor controller is a node. They don't call each other's functions directly; they publish and subscribe to topics, which are just named, typed data streams. Think of it the way I think about a wiring harness on a physical robot: each wire (topic) carries one signal type (message), and any component that needs that signal taps into the harness instead of running a dedicated line to the source.

ros2 topic list
ros2 topic echo /joint_states
ros2 node list

Those three commands got me further than any tutorial diagram. topic list shows you the harness; topic echo lets you probe a wire like a multimeter; node list shows you every component currently powered on. rqt_graph draws the whole harness diagram for you — genuinely the closest thing ROS 2 has to a wiring schematic, and the first tool I reach for on an unfamiliar stack.

Field note A message type is a connector shape. A publisher and subscriber on the same topic name but different message types simply won't "mate" — ROS 2 won't crash loudly, the subscriber just never receives anything. The first time this happened to me I spent an hour debugging a "dead" sensor that was actually publishing fine on a topic I was listening to with the wrong type.

Intermediate Workspaces, launch files, and the assembly analogy

A ROS 2 package is roughly a part file — one focused piece of functionality with its own dependencies. A workspace, built with colcon build, is the assembly: it pulls every package together and resolves how they connect. Once you have more than two or three nodes, you stop launching them by hand in separate terminals and write a launch file — the equivalent of an assembly drawing that specifies which parts go where, with what parameters, in what order.

For the quadruped footstep planner, my launch file had to bring up the Quad-SDK simulation bridge, the state estimator, and the planning node together, in the right sequence, with matched parameters (control frequency, robot description path, gains). Getting that launch file right was genuinely more finicky than the planning algorithm itself.

Services, actions, and when a topic isn't enough

Topics are fire-and-forget — good for continuous streams like IMU data or joint states. But sometimes you need a request/response: "compute this specific trajectory and tell me when it's done." That's a service (synchronous, blocking) or an action (asynchronous, with feedback and the ability to cancel). I use actions for anything with a duration and a possible failure — commanding a swing-leg trajectory, for instance, where I want progress feedback and the ability to abort mid-motion if a support-polygon guard trips.

TF2: coordinate frames without losing your mind

Every part in a CAD assembly has a coordinate system relative to its parent. TF2 is that same idea, live at runtime: it's a tree of coordinate frames (base_link → hip → foot, say) that ROS 2 keeps updated so any node can ask "where is the foot relative to the world, right now?" without every node needing to do its own forward kinematics.

Advanced QoS profiles and the sim-to-hardware bridge

This is the part that isn't in the beginner tutorials, and the part that actually mattered once I was fusing LiDAR, camera, IMU, and foot-force sensing into a single state estimate for the quadruped. Every ROS 2 topic has a Quality of Service (QoS) profile — reliability (best-effort vs. guaranteed delivery), history depth, and durability. A LiDAR scan publishing at 10 Hz and an IMU publishing at 400 Hz have no business using the same defaults.

Field note I lost the better part of a day to a planner node that silently received zero messages from a sensor node — both sides looked healthy in rqt_graph. The cause: one node used the default "reliable" QoS and the other used "best-effort," and ROS 2's DDS layer refuses to connect publishers and subscribers with incompatible QoS rather than degrading gracefully. Now checking ros2 topic info -v for QoS mismatches is one of the first things I do when a topic looks "connected" but silent.

The other advanced-but-unavoidable piece is bridging simulation and hardware. My footstep planner ran in MuJoCo through a ROS 2 bridge into Quad-SDK, converting foot targets into inverse-dynamics and swing-PD commands. The planning and learning logic didn't change between sim and hardware — but the timing did. Simulation can run faster or slower than real time and nothing complains; real actuators do not forgive a control loop that misses its deadline. That's where lifecycle nodes (nodes with explicit configure/activate/deactivate states) and ros2_control's hardware interface abstraction earn their complexity — they exist specifically to make the transition from "simulated joint" to "real motor with real latency" a configuration change instead of a rewrite.

Robotics Fundamentals · ~10 min read

How a robot decides where to step

"Motion planning" covers a wider range of problems than any one algorithm, and I learned that the hard way by working across very different ones: a Cartesian gantry loader with hard workspace limits, a SCARA arm doing inverse kinematics, and a quadruped deciding, twice a second, where its feet go next. This is the general landscape, not a single-algorithm deep dive — with the actual guards and heuristics I've used along the way.

Beginner Intermediate Advanced

Beginner Workspace vs. configuration space

The everyday meaning of "where is the robot" — its position in the room — is the workspace. But planning almost never happens there directly. It happens in configuration space (C-space): the space of every joint angle or actuator position the robot can take. A point in C-space fully describes the robot's pose; a path through C-space is a motion.

Why bother with the abstraction? Because obstacles are easiest to reason about in the workspace (a wall is a wall), but planning is easiest to execute in C-space (a valid path is one where every joint stays within its limits and nothing intersects). Motion planning is largely the work of translating one into the other. On the gantry loader, this was concrete and geometric: a 1500 mm lift and 1000 mm travel range with a rack-and-pinion drive meant the "obstacles" were mostly the machine's own physical limits, and the C-space was just two independent linear axes — about as simple as this problem gets.

Also worth knowing early: holonomic systems (like that gantry, or a drone) can move in any direction in C-space instantly; non-holonomic systems (a car, a legged robot mid-stride) have constraints on which directions they can move in right now, which is why a car can't strafe sideways into a parking spot and a quadruped can't teleport a foot without first lifting it.

Intermediate The three families

Most classical planners fall into one of three buckets:

Search-based

Discretize the space into a grid or graph and search it — A*, Dijkstra, D* Lite. Predictable, complete (they'll find a solution if one exists on the graph), and cheap in low dimensions. Great for 2D navigation; painful once you're searching a 6-DOF arm's joint space, because the grid grows exponentially with dimensions.

Sampling-based

RRT, RRT*, PRM. Instead of discretizing everything, randomly sample valid configurations and build a tree or graph connecting them. This is what makes high-dimensional planning (a 4-DOF SCARA arm, a 6-DOF manipulator) tractable — you never have to enumerate the full space, just enough of it to find a path. The tradeoff is that plain RRT gives you a path, not a good one; RRT* adds incremental rewiring to converge toward an optimal one given enough time.

Optimization-based

Formulate the trajectory as a numerical optimization — minimize a cost (distance, jerk, torque) subject to constraints (joint limits, obstacle clearance). CHOMP and TrajOpt are the well-known examples. These tend to produce smoother, more natural trajectories than sampling-based methods, but need a decent initial guess and are more sensitive to getting stuck in local minima.

Field note On the SCARA arm work, inverse kinematics gave closed-form joint solutions directly — no search needed, because a 4-DOF SCARA with the right joint layout has an analytical IK solution. The lesson that stuck: always check whether your problem has a closed-form or heuristic solution before reaching for a general-purpose planner. General planners are for when the structure of the problem doesn't hand you a shortcut.

Advanced Footstep planning: heuristics, guards, and learned residuals

Legged locomotion is a different kind of motion planning problem: you're not just finding a collision-free path, you're deciding where to place discrete contact points while keeping the robot balanced, dozens of times per second. This is the core of the work I did for my capstone.

The classical starting point is the Raibert heuristic: place the next foothold based on the body's velocity, a desired velocity, and the stance time, so the leg "catches up" to where the body is heading. It's cheap, real-time, and physically well-motivated — but it assumes flat, predictable terrain and doesn't adapt to irregularities it wasn't designed for.

The approach I built pairs that heuristic with a PPO-trained residual policy that outputs a 12-dimensional correction on top of the Raibert-nominal footholds — one 3D adjustment per leg. The heuristic still does most of the work; the learned policy only has to correct what the heuristic gets wrong, which is a much narrower thing to learn than locomotion from scratch. Three things made this safe enough to trust:

  • Workspace guards — reject any residual that would push a foot outside the leg's reachable volume.
  • Clearance guards — reject footholds that would cause a collision or an unreasonably short step.
  • Support-polygon guards — reject corrections that would leave the robot's center of mass outside the polygon formed by its planted feet, which is the geometric definition of "about to fall over."

These guards run analytically, not learned — so even a policy that's undertrained or exploring aggressively during training can't produce a foothold that's kinematically or statically invalid. It's the same instinct as the mechanical tolerance stack-ups I've done: define the hard limits explicitly, and let the flexible part of the system operate only inside them.

Trained to 1.25M steps and validated against square, circle, and figure-8 reference trajectories, the residual policy improved foot-placement quality on terrain the base heuristic wasn't tuned for, without the guards ever having to intervene during clean tracking — which is the result you want: the safety net there, but rarely pulled taut.

Mechanical Design × Robotics · ~9 min read

From CAD assembly to URDF

I spent three years designing Body-in-White sheet-metal structures in CATIA before I ever opened a URDF file. The first time I did, it felt like a bad translation of a language I already spoke fluently — the concepts all had CAD equivalents, but the dialect was different enough to cause real bugs. This is the map between the two, and the specific places I've watched that translation break.

Beginner Intermediate Advanced

Beginner Parts become links, mates become joints

A URDF (Unified Robot Description Format) file describes a robot as a tree of two elements:

  • Links — rigid bodies. In CAD terms, these are your parts (or rigid sub-assemblies). Each link carries three descriptions: visual (what it looks like — can be a detailed mesh), collision (a simplified geometry used for physics/collision checking), and inertial (mass, center of mass, and inertia tensor).
  • Joints — the connection between two links, with a type. This is your CAD mate, made explicit and typed: revolute (a pin joint with limits — a servo), continuous (a revolute joint with no limits — a wheel), prismatic (a slider — a linear actuator), or fixed (a rigid mate, no motion).
<joint name="link1_to_link2" type="revolute">
  <parent link="link1"/>
  <child link="link2"/>
  <origin xyz="0 0 0.05" rpy="0 0 0"/>
  <axis xyz="0 1 0"/>
  <limit lower="-1.57" upper="1.57" effort="10" velocity="2"/>
</joint>

Every one of Snakebot's 8 servo joints maps to a block almost exactly like this — the limit tag is literally the same physical constraint I calculated by hand from servo range and mechanical clearance during the original design.

Intermediate What CAD gives you for free, and what it doesn't

The single biggest advantage of coming from CAD: you already have accurate mass, center of mass, and inertia tensor for every part, computed from real geometry and material density — the exact inertial block URDF needs. Most robotics-first URDFs I've seen use rough guessed or default inertia values, because computing an inertia tensor by hand for an irregular shape is genuinely painful. If you're exporting from SolidWorks or CATIA, use that — it's usually more accurate than anything you'd hand-derive.

What CAD doesn't hand you automatically: axis and origin conventions. CAD assemblies are built around whatever reference geometry was convenient for design intent — often with Z as "up" but with no consistent convention for which way is "forward." ROS convention is X-forward, Y-left, Z-up, right-handed. When you export a mechanism designed with a different working axis (common, since design intent axes rarely match robotics convention), every joint's origin and axis tag needs to be re-derived, not just copied — get this wrong on one joint and everything downstream in the kinematic chain rotates about the wrong axis.

Xacro for the parts that repeat

Snakebot has 8 nearly identical joint modules; a SCARA arm has 4. Writing each out by hand in raw URDF is exactly the kind of repetitive, error-prone work CAD taught me to avoid with patterns and mate references. Xacro is URDF's answer — macros with parameters, so one template joint definition becomes 8 real joints differing only in their origin offset and name. It's the URDF equivalent of a CAD pattern feature.

Advanced Where the description stops matching the machine

A URDF that looks right and loads without errors can still be wrong in ways that only show up once you drop it into a physics engine.

Field note The first URDF I exported straight from a CAD assembly loaded fine in RViz — geometry looked correct, joints moved correctly — but the moment I dropped it into simulation, it exploded: links flying apart on the first physics step. The cause was an inertia tensor exported in the wrong units relative to what the exporter assumed, producing a physically implausible mass-to-inertia ratio. The visual and collision geometry were fine; the invisible inertial block was the actual bug. Now checking inertia values against a sanity estimate (mass × characteristic length²) is a standard step before trusting a new URDF in simulation.

A few other places the CAD-to-URDF translation gets lossy:

  • Collision mesh complexity — a detailed visual mesh exported straight from CAD will tank physics-engine performance if reused as the collision mesh. It needs to be decimated or replaced with primitive shapes (boxes, cylinders) or convex hulls — CAD accuracy is a liability here, not an asset.
  • Joint dynamics — CAD tells you nothing about damping or friction at a joint; those have to be measured or estimated and added manually (<dynamics damping="..." friction="..."/>), and they matter enormously for how a simulated joint actually behaves under control.
  • Simulator-specific extensions — Gazebo wants <gazebo> tags and plugin references; getting a URDF into MuJoCo typically means converting to MJCF, which has its own conventions for contacts and actuators. The base URDF is portable; the simulation-ready version rarely is, without extra work per target.
  • ros2_control transmissions — if the URDF is driving real hardware, joints need <transmission> tags and a hardware interface definition so ros2_control knows how to map a commanded effort or position to an actual motor driver — the software equivalent of the wire harness I'd have built by hand for Snakebot's PCA9685 driver.

The pattern across all of these: URDF wants a description that's simultaneously visually accurate, physically accurate, and computationally cheap, and CAD only naturally gives you the first two. The mechanical design background gets you most of the way there fast — it just doesn't get you the whole way for free.
